# Recommendations C: workspaces, console and platform quality

30 September 2026. Auditor C of three. Area: the host workspace (`app/host`),
the agent workspace (`app/agent`), the admin console and the staff and support
desks (`app/admin`, `lib/admin`), and platform-wide engineering quality.
Sixteen recommendations, C1 to C16, reported and not built.

**How this was made.** Read `docs/design/CLEAN_UNIFIED_DIRECTION.md`,
`docs/UIUX_30_RECOMMENDATIONS_2026-09-29.md` (the 30 items that just landed,
so none is repeated here), `docs/SUPPORT_STAFF.md`, `docs/PERF_SWEEP_2026-09-29.md`,
`docs/PASSCODE.md`, `docs/i18n/LOCALE_STATE.md`, `docs/VALLO_NATIVE_RELEASE_AUDIT.md`,
`docs/NATIVE_CI.md` and reference 38 in `docs/design/references/2026-09-29/`;
the host, agent and console code; read-only SQL against the live project
(counts cited below were taken on 30 September); and the GitHub Actions run
history. The shared dev server did not answer during this audit (every request
timed out after 60 to 120 seconds while it compiled), so no new screenshots
back these items; each claim cites a file, a query or a run instead.

**Rules kept.** Nothing here changes payment logic: the money items are read
only. No invented figures: every number is counted from the tree or the
database. Effort: S under half a day, M about a day, L two days or more.

## C1. Rates and nights on one calendar for hotels

- **Problem.** A hotel host can set how many rooms are open per night
  (`components/host/RoomNightsEditor.tsx`, a from/to date pair and a unit
  count per room type) but cannot change a price for any night. The table for
  that exists: `public.rate_calendar` (migration
  `20260918081453_m04_room_types_units_rate_plans_rate_calendar.sql`, "Nightly
  overrides for a rate plan: a different price, or a closed night"), and the
  database already prices from it (`20260929010846_perf_db_5_a_dated_search_reads_the_nights_it_prices.sql`,
  and the room booking pricing trigger in
  `20260929170728_room_bookings_1_...sql` "priced here from the host's rate plan
  and calendar"). No application file writes it: the only mentions in
  `apps/web/src` are the generated types and a schema-name test. The 1,980 live
  rows came from the example seed. `lib/host/actions.ts` offers
  `addRatePlanDraft` only, so a published rate cannot be edited at all.
  Weekend, festive (December in Lagos) and event pricing is how Nigerian hotels
  earn; today they would have to do it off Vallo.
- **Proposal.** A `/host/calendar` page (the spec's OPERATIONS group already
  names "calendar" in section 8.3): a month grid, one row per room type, each
  cell showing rooms open and the night's price. Drag or shift-click a range,
  then one sheet: set price, set rooms open, close, reopen. Presets: "Fridays
  and Saturdays", "this date range", "every night in December". Show the rate
  plan's base price in muted type and an override in ink, so a host always sees
  which nights differ. Booked nights are locked, as the agent calendar already
  does (`app/agent/listings/[listingId]/calendar/CalendarEditor.tsx`). Writes
  go through one server action that upserts `rate_calendar` and
  `room_inventory` under the owner's RLS; it prices nothing itself.
- **Impact.** Hotels can run their real pricing on Vallo; the priced search
  that already reads the calendar starts reflecting hosts' own decisions.
- **Effort** L. **Priority** P1.
- **Founder decision.** Whether a price change applies to requests already
  pending (recommend: no, a request keeps the price it was made at, which is
  what the trigger does today).

## C2. Calendar sync with other booking sites (iCal in and out)

- **Problem.** Lagos shortlet and hotel hosts almost always list on Airbnb or
  Booking.com as well. Vallo has no calendar import or export: no
  `text/calendar`, `VCALENDAR` or `.ics` handler anywhere in `apps/web/src`.
  The agent's per-listing calendar (`CalendarEditor.tsx`) and the host's room
  nights are edited by hand, so a night booked elsewhere stays open here until
  the host remembers. The first double booking on Vallo will be a trust story,
  and the Guarantee (`lib/money/copy.ts`) will be asked to pay for it.
- **Proposal.** Per shortlet listing and per room type: an export URL
  (a secret-token `.ics` feed of booked and closed nights, no guest names) and
  an import slot (paste another site's `.ics` link). A cron job
  (`lib/cron/jobs/`, beside `inventory-drift.ts`) pulls each import every 30
  minutes and writes closed nights with a source tag, never touching a night
  booked on Vallo. The calendar shows imported nights in their own tint with
  "From Airbnb, synced 12 min ago", and a failing feed raises a host notice
  after two failed pulls.
- **Impact.** Removes the largest operational risk of a multi-channel host,
  and removes the chore that makes hosts stop updating Vallo.
- **Effort** L. **Priority** P1.
- **Founder decision.** The sync interval (30 minutes is the market norm), and
  whether the export feed may be enabled for listings that are not yet
  published.

## C3. One "decide by" list for hosts, with the clock showing

- **Problem.** A pending stay request lapses after `HOLD_WINDOW_HOURS = 48`
  (`lib/bookings/checkout-view.ts`, swept by `lib/cron/jobs/hold-sweep.ts`).
  The agent's bookings workspace shows that window
  (`app/agent/bookings/BookingsWorkspace.tsx`, `t.card.releasingNow`), but the
  host's room requests (`app/host/bookings/page.tsx`,
  `RoomRequestAnswer.tsx`) and table requests
  (`app/host/reservations/ReservationsBoard.tsx`) never say by when the host
  must answer. The host home (`app/host/today.ts`) counts "requests waiting"
  but the rows sit on two different pages with two different looks.
- **Proposal.** A single "Decide" list in the host workspace: every pending
  room request and table request, sorted by time left, each row with a clock
  chip in the support desk's language (blue with time to spare, amber in the
  last quarter, red when it is about to lapse; `SUPPORT_STAFF.md`, "The promise
  and the clock"), and Accept / Decline inline through the existing actions and
  the landed confirm panel. A push and email reminder at the 75 per cent mark
  (the builders in `lib/push`, `lib/email` exist). The KPI tile "requests
  waiting" links here.
- **Impact.** Fewer lapsed requests, fewer disappointed guests; hosts learn
  that answering fast is the job.
- **Effort** M. **Priority** P1.
- **Founder decision.** Whether hosts get a published response-rate badge
  later (recommend: only once 20 or more requests exist per host).

## C4. Reviews that can reach a hotel, and a fair way to contest one

- **Problem.** Three gaps, all confirmed:
  1. `public.reviews.listing_id` is NOT NULL and there is no
     `accommodation_id` (live schema, 30 September). A hotel room booking has
     `listing_id` null (the `bookings_one_spine_chk` constraint in
     `20260929170728_room_bookings_1_...sql`), so no hotel stay can ever be
     reviewed once `room_bookings` is switched on.
  2. The host workspace has no reviews page at all (host nav:
     `components/host/host-nav-model.ts` has reservations, bookings, rooms,
     photos, arrival, transfer, earnings, assistant, settings). Agents have one
     (`app/agent/reviews/ReviewsWorkspace.tsx`, `ReplyForm.tsx`).
  3. A review can be reported (`lib/reports/categories.ts`, target `review`),
     but `reviews` has no status or hidden column, so staff can only leave it
     or delete it; the lister is told nothing either way.
- **Proposal.** (a) A review target for rooms and venues (an
  `accommodation_id` or `business_id` spine mirroring the bookings table),
  the eligibility rule unchanged: one review per completed stay. (b)
  `/host/reviews` on the agent pattern: list, reply, rating over time only
  once there are five or more. (c) "Ask Vallo to look at this review" for the
  lister, with the published criteria (off-topic, personal data, threats,
  not about the stay, conflict of interest), landing in the Reports lane with
  its own actions: keep, hide with a public note ("Removed by Vallo:
  personal information"), or redact a sentence. Both sides see the outcome.
- **Impact.** Stays get the trust signal that sells them; hosts get a fair
  process instead of a delete button; staff decisions are consistent.
- **Effort** L. **Priority** P1 (part a must land before `room_bookings` is
  turned on).
- **Founder decision.** The review criteria wording, and whether a hidden
  review still counts toward the rating (recommend: no).

## C5. Bulk actions and a freshness sweep for agents' listings

- **Problem.** `app/agent/listings/ListingsWorkspace.tsx` (837 lines) groups
  listings by status and acts on one card at a time: send for review, take
  down, delete, duplicate, close. An agent with 30 flats who lets five in a
  week, or who raises rents in January, repeats the same sheet 30 times. The
  admin queue already has multi-select and `bulkAct`
  (`app/admin/queue/page.tsx`); agents do not. There is no periodic "is this
  still available?" confirmation for the lister either (`lib/cron/freshness.ts`
  exists but nothing asks the agent to confirm stock), so stale listings are
  the renter's problem.
- **Proposal.** A select mode on the listings workspace (checkbox per card,
  shift-click for a range, "Select all in Live"), with a bottom action bar:
  Confirm still available, Take down, Send for review, Change price by amount
  or percentage (preview table of old and new, then the confirm panel). A
  weekly "Still available?" card on the agent home lists live listings not
  confirmed in 14 days, answerable in one tap per row or "All still available".
  Each bulk write loops through the existing per-listing actions so every
  guard and audit row stays as it is.
- **Impact.** Big portfolios become manageable; the catalogue stays fresh
  without staff chasing it.
- **Effort** M. **Priority** P2.
- **Founder decision.** Whether an unconfirmed listing is hidden after, say,
  30 days (recommend: demoted in ranking first, hidden at 45).

## C6. Keyboard layer and one lookup box for every desk

- **Problem.** Only the support desk has keys (`app/admin/support/SupportKeys.tsx`:
  j, k, n, c, r, m, e, ?). The listings review desk, KYC, moderation lanes,
  money decisions, and the host and agent workspaces have none. The console
  search (`ConsoleSearch` in `app/admin/_components/AdminNav.tsx`, Cmd or
  Ctrl K) only searches the desk you are on through its own `?q=`, so a staff
  member holding a reference from a phone call (a `VAL-SUP` ticket, a booking
  id, a Paystack reference, an email) has to guess which desk to open.
- **Proposal.** (a) Promote `SupportKeys` into a shared `useDeskKeys` with one
  sheet: j/k next and previous row, Enter open, a approve or accept, x decline
  or reject (always opening the confirm panel, never acting blind), g then a
  letter to jump desks (g q queue, g l listings, g k KYC), ? the list; never
  while typing. Host and agent get j/k, a, x on requests and g-jumps. (b) A
  console-wide lookup behind Cmd K: paste any identifier and get typed results
  ("Booking, 12 Oct, Grand Vista", "Ticket VAL-SUP-0042", "Member, joined
  August") each respecting the viewer's scopes (a support agent sees only
  what `requireAdmin("support")` allows, as today).
- **Impact.** Staff handle more items per hour with fewer clicks; a phone call
  gets answered from one box.
- **Effort** M. **Priority** P2.
- **Founder decision.** None.

## C7. An audit trail that puts people first

- **Problem.** `public.audit_log` holds 8,487 rows: 8,432 written by machines
  (`cron.*`, reconciliation and invariant runs) and 55 by anything else
  (live count, 30 September). Top actions: `cron.push-drain.ok` 1,978,
  `cron.canary.ok` 1,730, `cron.new-match-alerts.ok` 1,543. The trail is
  append-only (triggers `audit_log_no_update`, `no_delete`, `no_truncate`),
  which is right, but a staff decision is 1 row in 150. `/admin/audit` can
  filter by entity type (`lib/admin/audit-filter.ts`) yet opens on the
  mixture. Record pages do not show their own history except the booking
  detail (`app/admin/bookings/[bookingId]/page.tsx`); the listing review,
  the KYC subject and the person file do not.
- **Proposal.** (a) Clean runs of scheduled jobs go to a `job_runs` table (or
  one row per job per day with a count), and only non-clean runs stay in the
  trail; `/admin/operations` shows job health from it. (b) `/admin/audit`
  opens on "People" (actor is a person), with "Include scheduled jobs" as a
  toggle. (c) A shared `RecordHistory` panel (entity id filter, already
  supported by `audit-queries.ts`) on every record page: listing, KYC subject,
  business, person, agreement, ticket. (d) A weekly digest to the super admin:
  decisions per desk and per person, reversals, and access grants.
- **Impact.** The trail becomes something staff read, which is what makes it
  a deterrent; investigations take minutes, not a search.
- **Effort** M. **Priority** P1.
- **Founder decision.** How long job-run rows are kept (recommend 90 days;
  the audit trail itself follows `docs/RETENTION_SCHEDULE.md`).

## C8. Listing review triage: reason codes, saved notes, duplicate photos

- **Problem.** The listing review action bar
  (`app/admin/listings/[id]/ReviewActionBar.tsx`) takes a free-text reason.
  Two reviewers write the same rejection differently, the lister gets prose
  of uneven quality, and nobody can count why listings fail. Support has saved
  replies (`lib/admin/support-macros.ts`); listings do not. Duplicate-photo
  detection exists (`lib/photo-hash/dhash.ts`, `hash-server.ts`) but
  `listing_photo_hashes` holds 0 rows against 228 `listing_photos`, the
  backfill is a manual button (`PhotoBackfillButton.tsx`), and the queue
  (`ListingsQueue.tsx`, `rows.ts`) shows no duplicate signal.
- **Proposal.** (a) Reason codes chosen as chips, each with a lister-facing
  sentence from a reviewed library (Photos too few or unclear, Price missing
  a fee, Address does not match, Photos seen on another listing, Description
  too short, Wrong category), plus an optional free note. The lister sees the
  sentences as a checklist in the wizard. (b) Hash on upload and a nightly
  backfill job, so the table fills without anyone pressing a button. (c) Queue
  columns: "Photo seen elsewhere (n)", first-time lister, resubmission count,
  and time waiting; sorted by the promised review time. (d) Monthly "Why
  listings were sent back" chart on the analytics desk from the codes.
- **Impact.** Faster, fairer reviews; listers fix the right thing first time;
  recycled-photo scams get caught at the queue, not after a report.
- **Effort** M. **Priority** P1.
- **Founder decision.** The reason library wording (it is lister-facing copy).

## C9. Payout statements: every line of every payment, and an export

- **Problem.** Read only; nothing here changes how money moves. The money
  history model already carries `grossMinor`, `commissionMinor`,
  `guaranteeMinor` and `listerShareMinor` per entry
  (`lib/money/history-model.ts`), but the host and agent history lists
  (`components/app/money-history/HistoryList.tsx`) render only the amount and
  status; the breakdown appears only as period totals
  (`EarningsHistory.tsx`, `EarningsWorkspace.tsx`) and on the staff panel
  (`app/admin/_components/MoneyHistoryPanel.tsx`). There is no statement a
  host can give an accountant or the tax office, and no export for listers
  (only `lib/admin/money-export.ts` for staff).
- **Proposal.** Tap an earning to open its receipt: guest paid, Vallo
  commission, Guarantee contribution, your share, the Paystack reference, the
  bank it settled to (bank name and last four digits), and the booking link;
  the words from `lib/money/copy.ts` (`EARNINGS_SETTLEMENT`,
  `HISTORY_NOT_A_BALANCE`) stay. A "Statement" button per month produces a
  CSV and a printable page with the same lines and totals, reading the same
  RPC under the lister's session.
- **Impact.** Hosts trust what they cannot see (the split), and fewer support
  tickets ask "why is my payout less than the price?".
- **Effort** M. **Priority** P2.
- **Founder decision.** Whether the statement carries the company's name and
  RC number as a formal document (recommend: yes, with the Vallo Spaces Ltd
  details already on the legal pages).

## C10. Internal accounts left out of every figure

- **Problem.** Analytics are careful about example listings (`is_demo` is
  excluded in `lib/admin/reads/analytics.ts` and `reads/listings.ts`), but
  there is no marker for internal people. The live project has 16 accounts, at
  least 3 of them QA or test by their address, and staff (`staff_grants`: 3).
  Their views (`record_listing_views`), enquiries, bookings and sign-ups count
  in the agent funnels (`components/agent/ListingFunnels.tsx`), the admin
  analytics and the landing figures. At this scale one QA walk is a large share
  of the numbers. Separately, the per-listing funnel says views are counted
  (`t.shape.funnel.viewsCounted`) without saying since when; `listing_view_marks`
  and `listing_daily_stats` hold 0 rows today.
- **Proposal.** An `internal` flag on profiles, set by the super admin on the
  staff page and automatically for any staff grant; every analytics read and
  the view recorder skip internal actors; the admin analytics shows "Internal
  activity excluded" in its footer. Funnels and charts print "Counting since
  30 Sep 2026" from the first row, so a new counter never reads as a bad week.
- **Impact.** Figures agents and the founder act on stay true as the team
  grows.
- **Effort** S. **Priority** P2.
- **Founder decision.** None.

## C11. Hausa, Yoruba and Igbo: the 21 namespaces nobody has started

- **Problem.** `docs/i18n/LOCALE_STATE.md` (23 September) counts about 540
  undeclared keys per language. Since then the product has grown in 21 separate
  English modules merged into `en.ts` (`desk.en.ts`, `passcode.en.ts`,
  `frontDoor`, `platform`, `shape`, `trustVisible`, `afterTheGate`,
  `priceCheck`, `landlord`, `landingRooms`, the compliance set and more,
  4,541 lines of source together). None of them has a single key in `ha.ts`,
  `yo.ts` or `ig.ts`. That includes the passcode lock screen every member
  meets on every new session, and the new desk dashboards. On top, the host
  workspace pages pass English straight into props: about 46 literal
  `title=`/`body=`/`label=` strings in `app/host`, 25 in `components/host`,
  39 in `app/agent`, 175 in `app/admin` (for example `app/host/rooms/page.tsx`
  "Your rooms and your nights"). The completeness gate
  (`lib/i18n/locale-completeness.ts`) cannot see either gap by design.
- **Proposal.** (a) A coverage report per namespace per language in CI
  (declared, draft, missing), printed on every PR and in the doc. (b) A lint
  rule for `app/host`, `app/agent`, `components/host`, `components/agent`:
  no literal sentence in JSX text or in `title`, `body`, `label`,
  `placeholder`, `aria-label` props. (c) One speaker brief, ordered by reach:
  `passcode`, `desk`, `frontDoor`, the host workspace, then money copy. The
  admin console may stay English by decision.
- **Impact.** A Hausa-speaking host in Kano stops meeting English at the lock
  screen and across their whole workspace.
- **Effort** L (speaker time), the tooling M. **Priority** P1.
- **Founder decision.** Hire the three speakers; decide that the staff
  console is English-only (recommended), which removes 175 strings from scope.

## C12. CSS diet and one component per job

- **Problem.** `app/globals.css` imports 60 stylesheets into every page,
  1.6 MB of source CSS in `app/css`, including `wallet.css` (44 KB) for the
  wallet retired on 25 September (its only reference outside itself is a
  comment in `components/ui/Field.tsx`), `catalogue.css` (107 KB) and
  `landing-rooms.css` (75 KB). `admin.css` was already moved to the admin
  layout (B-4), which proves the pattern. About 100 of roughly 800 `nf-*`
  class roots defined in `app/css` have no literal reference in the TSX
  (a static count, so a few may be built dynamically). `tokens.css` is 215 KB.
  `perf-budget.json` has `budgetKb: null` on all eight routes, still lists
  `/wallet`, and lists no workspace route. Duplicates: two
  `ReservationsBoard.tsx` (host 277 lines, agent 231), two `LiveRefresh.tsx`
  and two `NoteForm.tsx` inside `app/admin`, two `RetryButton.tsx`, three
  `ThreadView.tsx`.
- **Proposal.** (a) Delete `wallet.css`; move landing, catalogue and
  workspace-only sheets to their route-group layouts as `admin.css` was; add a
  test that fails when `globals.css` imports a sheet whose classes are used
  only under one route group. (b) Run `scripts/check-weight.mjs --record` on a
  production build, fill every budget, drop `/wallet`, add `/host`,
  `/agent/dashboard`, `/agent/listings`. (c) A dead-class check in lint.
  (d) One `ReservationsBoard` in `components/app/desk/` used by both
  workspaces, one `LiveRefresh`, one `NoteForm`.
- **Impact.** Less CSS on every phone on a metered bundle; one fix lands in
  one place.
- **Effort** M. **Priority** P2.
- **Founder decision.** None.

## C13. Observability you can act on: crashes, references, quieter alerts

- **Problem.** The crash reporter is built (`lib/observability/report.ts`,
  `instrumentation.ts`) but `SENTRY_DSN` is not set in production
  (`VALLO_NATIVE_RELEASE_AUDIT.md` section 14), so no crash has ever been
  seen. Field vitals: `web_vitals_samples` has 6 rows (sampling 1 in 10;
  perf sweep open item 2). Error screens give a member nothing to quote to
  support. And alerting is noisy: `cron.sanctions-screen.attention` was
  written 420 times and `cron.pg-cron-watch.attention` 91 times, the latest
  on 29 September, which trains staff to ignore "attention". Scheduled jobs for
  switched-off features still run (`cron.landlord-line.ok` 561 times while
  the `landlord_line` flag is off).
- **Proposal.** (a) Set the DSN and add the source-map upload step the file
  itself describes. (b) Sample vitals at 100 per cent for two weeks, then
  back to 10. (c) Every error boundary prints a short reference (the digest's
  first 8 characters) with "Quote this to support"; the C6 lookup box finds
  the report by it. (d) Alert deduplication: one open alert per job and
  cause, re-raised only when the cause changes or after 24 hours, with an
  "acknowledged by" name on `/admin/alerts`. (e) Jobs check their feature flag
  first and log a skip, not a run.
- **Impact.** The first real crash is seen the day it happens; support can
  match a complaint to an error; alerts mean something again.
- **Effort** M. **Priority** P1.
- **Founder decision.** Set the Sentry DSN in Vercel (a founder-held account);
  agree who is on call for alerts.

## C14. Security that stays out of the way: passkey unlock and a key roster

- **Problem.** The passcode locks after 5 minutes idle or hidden
  (`lib/passcode/rules.ts`, `IDLE_LOCK_MS`) and wraps the workspaces too
  (`docs/PASSCODE.md`, "The gate"). A host on the front desk or an agent at a
  viewing types six digits many times a day. Biometric unlock is scoped but
  not built (`PASSCODE.md`: "the hook is `lib/passcode/native-unlock.ts`").
  For staff, the console key is a platform passkey proved every 12 hours
  (`ConsoleStepUp.tsx`: "Try again, on the device where you set it up"), and
  the staff page (`app/admin/staff/page.tsx`) shows no key status: nobody can
  see who has one key, who has two, or when each was last proved. A lost phone
  locks a staff member out with no written way back.
- **Proposal.** (a) "Unlock with Face ID or fingerprint": the WebAuthn
  ceremony the money lock already has (`lib/security/webauthn.ts`,
  `money-step-up.ts`) with an `unlock` purpose, offered after the third manual
  unlock on a device; the server writes the unlock cookie only after verifying
  it, as the doc requires. (b) On a device with a registered passkey, idle lock
  at 15 minutes instead of 5, stated in Settings. (c) A key roster on the staff
  page: keys per person, device label, added, last proved; a warning chip for
  anyone with one key; super admins must hold two. (d) A written break-glass
  path: a second super admin revokes the lost key and issues a one-time
  enrolment link, both audited.
- **Impact.** Fewer daily interruptions for the people who use Vallo most,
  and no staff lockout becoming a founder emergency.
- **Effort** M. **Priority** P1.
- **Founder decision.** The 15-minute idle rule on passkey devices, and who is
  the second super admin.

## C15. Native: from "it compiles" to "it was tried on a phone"

- **Problem.** `VALLO_NATIVE_RELEASE_AUDIT.md` still says no Gradle build has
  ever run, but the `native-android.yml` workflow has 33 runs and the recent
  ones succeed (GitHub Actions, 29 September), so the doc is behind the truth.
  What is still true: "Nothing has been tested on a device, by anyone, ever"
  (section 18), push tokens are not re-registered at launch (F-14), the
  permission read always answers `default` (F-15), and 3-D Secure inside the
  web view is unverified (F-16). For hosts and agents the shell matters most:
  a missed push is a lapsed request (C3).
- **Proposal.** (a) Add an Android emulator job to `native-android.yml` that
  installs the debug APK and runs the P0 rows of `VALLO_NATIVE_TEST_MATRIX.md`
  that need no account (launch, offline card, deep link to `/open`, back
  button, keyboard inset), with screenshots as artifacts. (b) Fix F-14 and F-15
  together: on each launch read the real permission through the Push plugin
  and re-register silently when granted. (c) Update the release audit's

## C16. Accessibility and end-to-end tests for the three desks

- **Problem.** axe runs in 8 component tests (`lib/a11y/axe.ts` callers:
  listing detail, gallery, filters, shell landmarks, app band, passcode gate,
  document uploader, AI consent); none covers the new desk primitives
  (`components/app/desk/DeskSidebar.tsx`, `KpiTile`, `Gauge`, `ConfirmPanel`)
  or any host, agent or console page. `apps/web/tests` has specs for agent
  listings, messages, reviews and calendar, and for admin, but none for the
  host workspace. The redesign changed every desk's frame at once, which is
  exactly when regressions land.
- **Proposal.** (a) An axe pass over the preview harness routes
  (`app/(dev)/preview/f5/*`: host-landing, agent-dashboard, agent-listings,
  admin-overview, admin-queue, confirm) at 390 and 1440 in both themes, failing
  CI on serious or critical findings. (b) A focus-order check for the confirm
  panel: focus lands on the title, Escape closes, focus returns to the button
  that opened it. (c) A `host.spec.mjs` on the pattern of the agent specs:
  every host route answers a designed state signed out and signed in, with a
  way back. (d) Keyboard-only walk of the sidebar and a table desk.
- **Impact.** The desks people work in all day stay usable with a keyboard
  and a screen reader, and redesigns stop silently breaking them.
- **Effort** M. **Priority** P2.
- **Founder decision.** None.
