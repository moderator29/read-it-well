# Vallo video calling: the founder's brief (8 October 2026, verbatim in substance)

The founder: "This is a big feature okay?? Think it deep and make the decision okay deep and get an agent and you on it okay? ... build it all and architect it deeply so it works and test it all end to end."

## His framing

Video calling becomes part of the property transaction and trust system, not just a button inside chat. Two stages: first video calls inside Vallo Messages, then scheduled verification and review calls inside the Admin Panel, on ONE shared calling infrastructure.

Providers to investigate before committing to one: LiveKit (first choice to evaluate; managed cloud plus open-source server; livekit.io, docs.livekit.io, cloud.livekit.io, livekit.com/pricing), Agora (web, React, iOS, Android, React Native SDKs; evaluate Capacitor; agora.io, docs.agora.io, agora.io/en/pricing), Daily (fast embedded calls; daily.co, docs.daily.co, daily.co/pricing/video-sdk). Investigate LiveKit first, compare Agora and Daily against the real codebase, pick ONE with documented evidence. Do not integrate all three. Cost is per participant-minute (a 10-minute two-person call is 20 participant-minutes).

Where it belongs:
- A. Messages, first release: call button in a conversation; incoming call screen with accept/decline; outgoing ringing and cancel; camera and microphone controls; switch camera, speaker/audio controls, reconnecting state; call history and missed-call markers in chat; back to the conversation when the call ends.
- B. Space and property journeys: tenant and landlord; buyer and agent (verified or not, trust status shown); buyer and seller; guest and hotel or short-let operator; customer and restaurant, event space or business; viewing consultations and remote walkthroughs. Calls launch from the space, inquiry or conversation so the context is kept.
- C. Admin Panel review calls: an authorised admin requests or schedules a call with a landlord, agent, realtor, hotel operator, business owner or service provider; in-app invitation and notification; reason, case reference and profile shown; live identity/business/listing review; outcome, evidence references and follow-ups recorded; escalation. Joining a call does not itself verify identity or ownership.
- D. Mobile and Capacitor: web, iOS and Android. Inspect how the Capacitor app loads the production site, handles permissions, resumes from notifications and deep links. A browser-only integration is not assumed to work in the native shell.

Architecture: calls are a Vallo domain system; the provider is media infrastructure only.
Vallo video experience (Messages, space pages, business workspaces, admin review) -> Vallo Call Orchestrator (permissions, lifecycle, scheduling, invitations, authorisation) -> Vallo database (calls, participants, context, audit events) and Notifications (incoming, invites, missed) -> Secure provider adapter (server-issued short-lived tokens, provider webhooks, usage reconciliation) -> the selected provider (live audio/video, room connection, media transport). Never expose provider secrets to the browser; never let a client mint its own unrestricted room token.

Launch order: 1) one-to-one audio/video in Messages; 2) notifications, missed calls, call history, mobile compatibility; 3) admin-scheduled review calls with structured outcomes; 4) space walkthroughs, richer business workflows, optional group calls; 5) recording or transcription only with a real need and privacy/legal controls.

"Don't let Claude merely install a video SDK and announce that video calling is done. The real work is making the invitations, permissions, native mobile experience, call states, notifications, admin workflow and failure recovery all work together."

## The master prompt (his, verbatim in its requirements)

VALLO VIDEO CALLING SYSTEM: research, provider selection, architecture, end-to-end implementation plan and release audit. Audit and extend the existing platform; do not replace the chat system or rewrite unrelated features.

PHASE 0, investigate before changing anything: monorepo structure and scripts; current messaging; schema, migrations, RLS and realtime; notifications, push, deep links, routing; auth, identities, workspaces, roles, admin permissions; user/owner/landlord/agent/realtor/hotel/business/admin experiences; Capacitor config, native projects, camera/mic permissions, WebView behaviour; design system, themes, a11y, loading/error states; deployment, env conventions, background jobs, logging, monitoring, webhooks; any existing voice/video/media. Confirm everything in the repo. No duplicate messaging services, notification systems, call-state stores or tables. Write a baseline report.

PHASE 1, provider research from official docs: web/React/Next.js SDK fit with the current React version; iOS/Android/Capacitor/WebView compatibility and whether native plugins are needed for background calls and push-to-call; browser support and permissions; quality on weak mobile networks; TURN/relay; screen share and multi-party later; token creation, expiry, room access, participant permissions; room create/delete; webhooks and server-side verification; recording and consent; quality analytics; regions and data residency; usage pricing, free allowances, bandwidth, recording costs, minimums; lock-in; security, encryption, privacy terms, DPA; limits and support. Current official pricing only, no invented costs. Comparison matrix with source links, one recommendation, a reasoned second choice, why the others lost. ONE provider, behind an interface that allows a later swap. If credentials are missing, continue with architecture, code and sandbox/test validation; never claim a live call was tested when it was not.

PHASE 2, product experience. A) Messages: audio and video initiation; incoming notification; incoming screen accept/decline; outgoing ringing; cancel; busy, unavailable, rejected, unanswered; permission request and denied recovery; camera and mic controls; camera switch; speaker/audio device where supported; connection status and reconnecting; network recovery; remote left/disconnected; duration; end-call confirmation where appropriate; missed-call indication; history in the conversation; return to the exact conversation; notification and deep-link behaviour; clear failures with retry. Vallo design system and navigation; no external meeting app unless a documented platform limit forces it; no public guessable room links. B) Space-related entry points (tenant-landlord, buyer-seller/agent, guest-hotel/short-let, customer-restaurant/venue/business, business-service provider, scheduled walkthrough), keeping references to conversation, listing, space, workspace or inquiry; only where they make sense in the product and authorisation model. C) Admin review calls: select an authorised user or case; purpose and case reference; schedule or immediate; notify; participant accepts, declines or asks for another time; join a secure Vallo session; show only authorised case info; record metadata and attendance; structured notes, outcome, follow-ups, evidence references; complete, escalate or reschedule. Outcomes: REVIEW_COMPLETED, MORE_INFORMATION_REQUIRED, FOLLOW_UP_REQUIRED, ESCALATED, NO_SHOW, CANCELLED. Reuse existing case and verification workflows. A review call is not proof of identity, ownership, licensing or authenticity. No unrestricted "any staff can call any user": role permission, case access, auditable purpose, least privilege.

PHASE 3, calling domain: CallOrchestrator, CallAuthorizationService, CallInvitationService, CallSchedulingService, CallTokenService, CallStateService, CallNotificationService, CallHistoryService, CallWebhookService, CallAuditService, CallUsageService, AdminReviewCallService, provider adapter (logical responsibilities, following Vallo's service patterns, not a swarm of tiny files). Provider-neutral interface: prepare a room, issue participant credentials, end a room, process provider events, read quality/usage, map provider errors. Provider SDK imports stay inside the adapter boundary. Backend is the source of truth. Lifecycle: CREATED -> INVITATION_PENDING -> RINGING -> ACCEPTED -> CONNECTING -> ACTIVE -> ENDED; also DECLINED, CANCELLED, MISSED, BUSY, FAILED, EXPIRED, INTERRUPTED. A disconnect is not an end while reconnection is possible. Legal transitions enforced server-side, timestamps stored, no duplicate acceptance, no conflicting active calls where unsupported, no replayed invitations, no unauthorised participants; timeouts and scheduled transitions defined.

PHASE 4, data model: reuse users, conversations, messages, workspaces, listings, cases, notifications, audit. Smallest coherent set of new entities (candidates: calls, call_participants, call_events, call_schedules, call_invitations, call_provider_events, call_quality_summaries, admin_review_sessions, admin_review_notes, admin_review_evidence_links; explain the final choice). A call record holds: internal id; AUDIO or VIDEO; initiator; conversation; optional listing/space, workspace, admin review case; state; provider and provider room ref; created/ringing/connected/ended/expiry timestamps; duration where reliable; termination reason; scheduling; authorised participants; audit and reconciliation refs. Opaque ids; server-controlled provider ids; no tokens, secrets, sensitive metadata or risk signals in message history; retention, deletion, access and audit rules.

PHASE 5, token security: server-side issuance only, by the provider's recommended production method. Before issuing: authenticated; call exists, not expired or cancelled; user is an authorised participant or reviewer; state allows joining; user not removed/blocked/restricted; workspace and conversation permissions allow it; admin review access valid for the case. Short-lived, room- and participant-scoped, least permission. Secrets never in browser or app bundles, public env vars, logs or errors. Rate limits, abuse controls, validation, replay resistance; webhooks authenticated per the provider, idempotent and retry-safe. Never trust client-supplied status, duration, identity or provider payloads.

PHASE 6, messaging: reuse the message infrastructure and its structured/system message types; system events for outgoing, incoming, missed, declined, completed, scheduled invitation, rescheduled. No tokens in messages. One canonical source of truth for call history. Realtime for both sides; duplicates, reconnecting clients, stale screens, simultaneous actions handled; blocking, reporting, conversation access and workspace membership respected.

PHASE 7, notifications and deep links: existing infrastructure; in-app, push and web for incoming, missed, scheduled review invitations, accepted/declined, rescheduled, upcoming, cancelled. Deep links route only after auth checks; expired or unauthorised links get a safe recovery screen; no tokens or sensitive review details in URLs or push payloads. Foreground, background, killed and resume handled separately. No claim of CallKit, ConnectionService, lock-screen or reliable background incoming calls unless built and tested.

PHASE 8, Capacitor: audit the native shell loading the remote production site: camera/mic permissions and denied recovery; secure context; WebRTC in the real iOS and Android WebViews; audio routing and camera switch; background/foreground; Wi-Fi/mobile switch; Bluetooth/wired audio; deep links; notification taps; WebView lifecycle and media-track cleanup; safe areas, orientation, keyboard; reconnection; release-build config. Native plugins only after checking the current Capacitor version. No Expo rewrite, no separate app. Document limits and native config.

PHASE 9, admin security and audit: explicit permissions for viewing sessions, creating invitations, scheduling/rescheduling, joining, reading notes, adding evidence, completing/escalating, viewing sensitive case details. Append-only audit (actor, action, resource, time, reason). No credentials, tokens, unnecessary personal data or private conversation content in logs. Sensitive notes only for authorised staff. Corrections without silently overwriting history. No hidden way for admins to enter private calls, switch on cameras or mics remotely, or record people without their knowledge.

PHASE 10, recording, consent, privacy: default no recording. Recording or transcription only as a separately gated capability with business need, provider review, legal/privacy review and explicit disclosure and consent; never silent. For admin reviews keep attendance and authorised outcomes, not the conversation. List the legal/privacy questions (Nigerian NDPA and others) for qualified review.

PHASE 11, premium UX: Vallo tokens; premium incoming and outgoing screens; clear identity and context; elegant controls; restrained motion; light and dark; accessible labels; loading, permission, connecting, reconnecting, failure states; responsive; safe areas; reduced motion; keyboard and screen reader; correct back and end behaviour. Not a generic conferencing dashboard; no excess glass or clutter; usable on small screens; keep the user oriented.

PHASE 12, costs, abuse, operations: totals, completed/missed/failed, audio vs video, participant-minutes, average duration, connection success and setup time, reconnection rate, provider quality metrics and errors, estimated vs reconciled cost (kept distinct). Configurable controls on initiation, invitation frequency, concurrency, max duration, suspicious activity, without blocking legitimate customers. No unauthorised room creation. Alerts and procedures for outages, billing limits, webhook failures and degradation.

PHASE 13, testing: unit (lifecycle, authorisation, membership, token rules, invitation expiry, scheduling, webhook signature and idempotency, notification dedupe, admin permissions, provider errors); integration (create, invite, accept/decline, both join, complete, missed, expired, unauthorised and cross-workspace attempts, admin scheduling and completion, repeated and out-of-order webhooks, provider outage); end to end (A starts a video call in a conversation, B receives and accepts, both join, audio and video work, mute/camera/end work, history correct, notifications consistent; then admin schedules a review, the landlord/agent/business receives and accepts, both join, admin completes, notes and outcome stored with correct access and audit); devices where available (desktop and mobile browser, iOS and Android release builds, denied permissions, weak network, network switch, background/resume, deep links, notification taps). Automated, simulated-provider and real-device tests reported separately; never report a simulated test as a real call.

PHASE 14, plan and release: findings, provider comparison and recommendation, architecture, DB changes, API contracts, authorisation matrix, journeys, admin workflow, mobile/native requirements, cost assumptions and unknowns, security and privacy risks, phases, test plan, rollback, env vars and setup. Backward-compatible migrations, feature flags, staged rollout; nothing destructive; existing functionality preserved.

Deliverables (in this folder): VIDEO-CALLING-RESEARCH.md, VIDEO-CALLING-ARCHITECTURE.md, VIDEO-CALLING-PROVIDER-DECISION.md, VIDEO-CALLING-API-CONTRACTS.md, VIDEO-CALLING-SECURITY-PRIVACY.md, VIDEO-CALLING-ADMIN-REVIEWS.md, VIDEO-CALLING-MOBILE-COMPATIBILITY.md, VIDEO-CALLING-TEST-REPORT.md, VIDEO-CALLING-PRODUCTION-CHECKLIST.md, VIDEO-CALLING-OPEN-QUESTIONS.md. The final report states what existed, the provider chosen and why, what was built, what was tested, what passed and failed, whether a real provider-backed call was completed, whether iOS and Android release builds were tested, what is blocked (credentials, devices, legal, provider setup), outstanding security issues, and exact next steps for launch. Never claim end-to-end completion without evidence.
