> **Track A, 25 September 2026.** Vallo no longer holds customer money: the wallet, escrow and held payments are retired. Where this document describes them it describes the past; the current truth is [`docs/MONEY_ARCHITECTURE.md`](/docs/MONEY_ARCHITECTURE.md).

Research only. Nothing in this file has been applied. No product code was
modified, no migration was written, no database was touched, and git was not
run. The one file this session wrote is this one.

Every claim about our own code carries a `path:line`. Every claim about the
outside world carries a source. Where I could not verify something I say so,

British spelling throughout. No em dash characters anywhere in this file,

# PART 1. THE EMAIL LAYER AS IT STANDS

## 1.1 The headline, before the detail

The brief assumed a thinner layer than the one that is here. What is actually
built:

- A hand written Resend client over `fetch`, with no SDK, no `nodemailer`, no
  `react-email`, no SMTP anywhere in the application.
- A block based render layer that emits HTML and `text/plain` from one
  description, so the two cannot drift.
- A catalogue of twenty transactional messages plus two account deletion
  messages, all dark, all on one palette.
- Five Supabase auth templates generated by a Node script into
  `supabase/templates/`, with plain text twins.
- A Send Email Hook endpoint, already written, already signature verified,
  that routes every Supabase auth email through our own sender and our own
  template.

What is missing is not the machinery. It is that ten of the twenty catalogue
messages have no call site, the welcome email among them, and that the
repository's own documentation disagrees with the repository's own code about
which Supabase path we are on.

### Built and never sent: ten, not nine

The previous audit's number was nine. I counted ten. Each of these has zero
non-test, non-fixture call sites; I verified builder by builder with a scripted
grep over `apps/web/src`.

1. **`welcome`**, `apps/web/src/lib/email/messages.ts:212`.
   Five role specific welcomes plus a general one, fully written. Nothing calls
   it. The reason it never fires is that no code path runs after a successful
   sign-up confirmation: `signUpWithEmail`
   (`apps/web/src/lib/auth/actions.ts:288`) creates the user and stops, and
   `verifyOtp` (`apps/web/src/lib/auth/actions.ts:433`) sets the session and
   redirects. Neither knows about the email catalogue. There is also no
   database hook: the signup trigger writes the profile and nothing else. This
   is the single largest gap in the system, because it is the one message every
   new account should get and the only one with no substitute anywhere.

2. **`passwordReset`**, `apps/web/src/lib/email/messages.ts:456`.
   Never called because Supabase owns this flow end to end.
   `requestPasswordReset` calls `supabase.auth.resetPasswordForEmail`
   (`apps/web/src/lib/auth/actions.ts:746`), which makes GoTrue render and send
   its own recovery mail. Our builder takes a `resetUrl` that only GoTrue can
   mint, so there is no way to call it from application code without the hook.
   With the Send Email Hook live, the hook route could reach it, but today the
   route sends `verificationCode` for every action type including `recovery`
   (`apps/web/src/app/api/auth/email-hook/route.ts:160-175`).

3. **`withdrawalOutcome`**, `apps/web/src/lib/email/messages.ts:536`.
   Covers `paid`, `failed` and `reversed` (`messages.ts:508`). The wallet paths
   call the narrower `withdrawalFailed` instead
   (`apps/web/src/lib/wallet/actions.ts:667`, `:879`;
   `apps/web/src/app/api/paystack/webhook/route.ts:469`). So a successful
   payout and a reversal both go unemailed: there is code for the good news and
   nobody wired it.

4. **`escrowFunded`**, `apps/web/src/lib/email/messages.ts:615`.
   No call site. The escrow movements write in-app notifications from the
   database (titles `Money is held for you`, `A release has been asked for`,
   `One side has confirmed`, `A decision on your escrow`,
   `This escrow is in dispute`, all `kind = 'wallet'`), and there is no
   application path that runs alongside those trigger writes to send mail.

5. **`escrowReleased`**, `apps/web/src/lib/email/messages.ts:664`. Same reason
   as above.

6. **`inspectionScheduled`**, `apps/web/src/lib/email/messages.ts:724`.
   The inspection lifecycle is entirely database side:
   `private.notify_inspection_change()`
   (`supabase/migrations/20260918120100_m11_an_inspection_tells_both_sides_what_happened.sql:100`,
   trigger at `:208`) writes in-app rows for requested, confirmed, declined,
   withdrawn, another time offered and complete. No server action in
   `apps/web/src` sits beside it to send the email.

7. **`listingApproved`**, `apps/web/src/lib/email/messages.ts:789`.
   The admin moderation path writes an audit row and the notification, and
   sends no mail. Nothing imports the builder.

8. **`listingRejected`**, `apps/web/src/lib/email/messages.ts:836`. Same as
   above.

9. **`verificationRungPassed`**, `apps/web/src/lib/email/messages.ts:896`.
   Four rungs are typed (`phone`, `identity`, `address`, `inspection`,
   `messages.ts:865`). No admin or automated path calls it.

10. **`newEnquiry`**, `apps/web/src/lib/email/messages.ts:945`.
    A lister hearing that somebody has messaged them about a listing. The
    in-app side exists: `private.notify_message()`
    (`supabase/migrations/20260729112606_notifications.sql:112`, trigger at
    `:140`) writes a `message` row on every insert. The email half was written
    and never attached to `apps/web/src/lib/messages/actions.ts`.

The pattern behind all ten: **every unsent message belongs to an event whose
in-app notification is written by a database trigger, or to an auth flow owned
by Supabase.** Every message that does send hangs off a Next.js server action or
an API route, which is the only place the current architecture can reach the
email client from. That is the real finding, and it is the thing a build
session has to design around, not ten separate oversights.

`apps/web/src/lib/email/fixtures.ts` renders all twenty for the test suite, and
`apps/web/src/lib/email/shell.test.ts:73` fails if a builder has no fixture, so
the unsent ten are tested, rendered and unshipped. They are also all visible on
the dev harness route `apps/web/src/app/(dev)/preview/g5/`.

## 1.5 The exact call a build agent must make

Send one catalogue message to one person. This is the whole contract.

```ts
import { bestEffortEmail, sendMessage } from "@/lib/email/client";
import { welcome } from "@/lib/email/messages";

await bestEffortEmail(async () => {
  const message = welcome({ name: firstName, role: "renter" });
  await sendMessage(recipientEmail, message);
});
```

Signatures, verbatim from `apps/web/src/lib/email/client.ts`:

```ts
// client.ts:166
export async function sendMessage(
  to: string,
  message: { subject: string; html: string; text: string },
  options?: { replyTo?: string },
): Promise<SendEmailResult>;

// client.ts:188
export async function bestEffortEmail(work: () => Promise<unknown>): Promise<void>;

// client.ts:100
export async function sendEmail(message: SendEmailMessage): Promise<SendEmailResult>;

// client.ts:77
export function isEmailConfigured(): boolean;

// client.ts:82
export function emailFrom(): string;
```

Five rules a build agent must not break:

1. **Call `sendMessage`, never `sendEmail`, for a catalogue message.** Spreading
   a message into `sendEmail` by hand is how the text part gets dropped, and the
   comment at `apps/web/src/lib/email/client.ts:156-165` says exactly that.
2. **Wrap every send in `bestEffortEmail`** except the auth hook. It skips the
   work entirely with no API key and swallows every failure, so a booking that
   saved stays saved (`client.ts:180-195`). The auth hook is the documented
   exception, because there the email *is* the work
   (`apps/web/src/app/api/auth/email-hook/route.ts:179-191`).
3. **Send after the database write has committed**, never inside the
   transaction. `apps/web/src/lib/bookings/actions.ts:20-24` states the rule.
4. **Resolve the recipient through `apps/web/src/lib/email/recipients.ts`**, not
   by reading `profiles` at the call site. `contactForSelf`
   (`recipients.ts:77`), `contactForUser` (`recipients.ts:129`) and
   `contactForAgent` (`recipients.ts:152`) each take an `EmailChannel` and
   return `null` when the person has switched that channel off, which is how
   the settings promise is kept in one place rather than at every send site
   (`recipients.ts:29-38`). The four channels are `bookings`, `messages`,
   `wallet`, `marketing` (`recipients.ts:39`).
5. **Watch the name collision.** `apps/web/src/lib/messages/actions.ts:407`
   also exports a function called `sendMessage`, and it posts an in-app chat
   message. Two different things, same name, both imported as `sendMessage`. A
   build agent that autocompletes the wrong one will silently post a chat
   message instead of sending an email. Import the email one as
   `import { sendMessage } from "@/lib/email/client"` and check the path.

If a new message is added to the catalogue, `shell.test.ts:73` requires a
fixture in `apps/web/src/lib/email/fixtures.ts` or the suite fails.

## 1.7 Supabase Auth as our code uses it today

Every call, with its line:

| Flow | Call | Line |
| --- | --- | --- |
| Password sign-in | `signInWithPassword` | `apps/web/src/lib/auth/actions.ts:244` |
| Sign-up | `signUp` with `emailRedirectTo` and rich `data` metadata | `apps/web/src/lib/auth/actions.ts:288` |
| Confirm sign-up by code | `verifyOtp({ email, token, type: "signup" })` | `apps/web/src/lib/auth/actions.ts:433` |
| Confirm by link, PKCE | `exchangeCodeForSession` | `apps/web/src/lib/auth/actions.ts:554` |
| Confirm by link, token hash | `verifyOtp({ token_hash, type })` | `apps/web/src/lib/auth/actions.ts:565` |
| Resend the sign-up code | `auth.resend({ type: "signup" })` | `apps/web/src/lib/auth/actions.ts:625` |
| OAuth | `signInWithOAuth` | `apps/web/src/lib/auth/actions.ts:676` |
| Password reset request | `resetPasswordForEmail(email, { redirectTo })` | `apps/web/src/lib/auth/actions.ts:746` |
| Set the new password | `updateUser({ password })` | `apps/web/src/lib/auth/actions.ts:800` |
| Re-auth before deletion, by code | `signInWithOtp` then `verifyOtp` | `apps/web/src/lib/account-deletion/reauthenticate.ts:54`, `:94` |

**Code or link? Both, and that is deliberate.**

- Sign-up confirmation is a **six digit code**. The screen at
  `apps/web/src/app/(auth)/sign-up/verify/page.tsx` asks for six digits and
  `apps/web/src/lib/auth/actions.ts:433` verifies `token` plus `email`.
- The same flow also accepts a **link**: `completeEmailVerification`
  (`apps/web/src/lib/auth/actions.ts:540-580`) handles a PKCE `code`, a
  `token_hash` with a type, or an access and refresh token pair, and the callback
  page at `apps/web/src/app/auth/callback/page.tsx` drives it. Both halves work,
  which `AUTH_EMAILS.md` section 2 also states.
- Password reset is **link only** today. `resetPasswordForEmail` sends the
  recovery link to `/auth/callback?next=/reset-password`
  (`apps/web/src/lib/auth/actions.ts:747`), the callback exchanges it and
  `updatePassword` acts on the session that exchange created
  (`apps/web/src/lib/auth/actions.ts:800`). There is no six digit recovery
  screen.
- The code length and lifetime are Supabase settings: `otp_length = 6` and
  `otp_expiry = 3600` (`supabase/config.toml`, the `[auth.email]` block). The
  hook route restates sixty minutes at
  `apps/web/src/app/api/auth/email-hook/route.ts:56`.

One local configuration note worth flagging: `enable_confirmations = false` in
the `[auth.email]` block of `supabase/config.toml`. Locally, sign-ups are not
required to confirm. That is the local CLI file and not necessarily the hosted
project's setting, and I could not read the hosted project's settings.

## 1.8 The Supabase side: where the documentation and the code disagree

This is the most important finding in Part 1 after the unsent ten.

`AUTH_EMAILS.md` section 1 says, in terms, that we chose **custom SMTP** over
the Send Email Hook, and gives the reasoning: "the hook means an endpoint we
host, a shared secret, and an outage in our deployment becoming an outage in
sign-up".

But the hook endpoint exists, is complete, and is better than that document
assumes:

- `apps/web/src/app/api/auth/email-hook/route.ts`, 194 lines.
- Standard Webhooks signature verification over the raw body, timing safe, with
  a five minute skew bound (`:109-129`).
- It refuses everything without `SUPABASE_AUTH_HOOK_SECRET` (`:110`, `:143`),
  by design, because the endpoint sends mail to any address in its body.
- It sends `verificationCode` for every action type and explains why one
  message covers all of them (`:160-175`).
- It returns 502 when the send failed so Supabase retries (`:179-191`).
- `.env.example:208-212` documents the secret.

So the code is on the hook path and the documentation is on the SMTP path. A
build session must not treat `AUTH_EMAILS.md` as current. Someone has to decide
which one is live, and the decision changes what the founder clicks.

There is a second consequence nobody has written down: **with the hook enabled,
the five generated templates in `supabase/templates/` stop being used at all.**
The hook replaces Supabase's built-in email sending entirely, so GoTrue never
renders a dashboard template. Those five files and the generator behind them
(`scripts/build-auth-emails.mjs`, 5 HTML + 5 txt, about 54KB total) become the
SMTP fallback only. They are still asserted byte for byte by
`shell.test.ts:413`, so they will not rot, but they will not ship either.

## 1.9 Making Supabase Auth send through Resend with our templates

Two routes. They are mutually exclusive in practice: with the hook enabled,
GoTrue does not render templates or use SMTP for auth mail.

### Route A, custom SMTP. Simpler, and our templates render inside Supabase.

What the founder clicks (dashboard only):

1. **Resend, Domains, Add domain**, `vallospaces.com`. Publish the DKIM, SPF
   and DMARC records it prints at the registrar. Wait for verified. Until
   verified, Resend delivers only to the account owner's own address.
2. **Resend, API Keys**, create a key with send permission on that domain.
3. **Supabase Dashboard, Project Settings, Authentication, SMTP Settings**,
   enable custom SMTP and fill in:

   | Field | Value |
   | --- | --- |
   | Host | `smtp.resend.com` |
   | Port | `465` (`587` also works) |
   | Username | `resend` |
   | Password | the Resend API key |
   | Sender email | `hello@vallospaces.com` |
   | Sender name | `Vallo` |

4. **Supabase Dashboard, Authentication, Rate Limits.** Saving custom SMTP
   imposes a low rate limit of **30 messages per hour** to protect the new
   sending reputation, and it has to be raised deliberately. This is documented
   by Supabase and it is the single most common launch-day surprise.
5. **Supabase Dashboard, Authentication, URL Configuration.** Site URL must be
   the real deployment origin. Every auth template loads the lockup from
   `{{ .SiteURL }}/brand/`, so with Site URL on localhost every auth email
   ships a broken lockup (`AUTH_EMAILS.md` section 2).
6. **Supabase Dashboard, Authentication, Email Templates.** Paste each
   generated file and set the subject beside it:

   | Action | File | Subject |
   | --- | --- | --- |
   | Confirm signup | `supabase/templates/confirmation.html` | `Confirm your Vallo email` |
   | Magic Link | `supabase/templates/magic-link.html` | `Your Vallo sign-in link` |
   | Reset Password | `supabase/templates/recovery.html` | `Set a new Vallo password` |
   | Change Email Address | `supabase/templates/email-change.html` | `Confirm your new Vallo address` |
   | Invite user | `supabase/templates/invite.html` | `You have been invited to Vallo` |

What a build session writes: **nothing.** Route A is entirely dashboard work.
The one code task is to run `node scripts/build-auth-emails.mjs` if the
generator has changed, because the dashboard is pasted from its output and
`shell.test.ts:413` proves the committed files match the generator.

Route A limitations, stated honestly:

- The dashboard has one HTML field per action and **no field for a text part**.
  Whether GoTrue attaches a text alternative of its own is not something this
  repository can prove (`AUTH_EMAILS.md` section 4 says the same). The `.txt`
  twins exist and are unused on this route.
- No per-user language, no per-user logic, no fallback provider.
- The default Supabase SMTP service, which is what runs until step 3, only
  delivers to addresses on the project's own team and is explicitly documented
  as non-production.

### Route B, the Send Email Hook. Already built here, and strictly more capable.

What the founder clicks:

1. Steps 1 and 2 of Route A. The domain still has to be verified in Resend,
   because we are the sender now.
2. **Supabase Dashboard, Authentication, Hooks, Send Email hook.** Create it,
   choose **HTTPS** as the type, and set the URL to
   `https://vallospaces.com/api/auth/email-hook`.
3. Click **Generate Secret**. Supabase shows it as `v1,whsec_<base64>`. Copy
   the whole string.
4. Save the hook.
5. **Vercel, Project Settings, Environment Variables.** Paste the whole string
   into `SUPABASE_AUTH_HOOK_SECRET`. Our parser accepts it with or without the
   `v1,` and `whsec_` prefixes (`route.ts:90-100`).
6. Confirm `RESEND_API_KEY` and `NEXT_PUBLIC_SITE_URL` are set in the same
   environment, because the hook sends through our client and our client builds
   absolute URLs from the site URL.
7. Redeploy so the new environment variables are live, then sign up with a
   throwaway address and confirm the six digits arrive from Vallo.

What a build session writes: the endpoint already exists, so the remaining code
work is the part the hook makes possible and nobody has taken:

- **Branch on `email_action_type`.** The payload carries it
  (`route.ts:61-80`), and today every type gets `verificationCode`
  (`route.ts:171`). The Supabase payload is documented as:

  ```json
  {
    "user": { "id": "...", "email": "...", "user_metadata": { ... } },
    "email_data": {
      "token": "305805",
      "token_hash": "7d5b...",
      "redirect_to": "https://vallospaces.com/",
      "email_action_type": "signup",
      "site_url": "https://...",
      "token_new": "",
      "token_hash_new": "",
      "old_email": "", "old_phone": "", "provider": "", "factor_type": ""
    }
  }
  ```

  So `recovery` can call `passwordReset` with a URL built from
  `redirect_to` plus `token_hash`, which retires unsent message number 2
  above. `email_change` can name both addresses. `invite` can carry its own
  words.
- **Send the welcome.** The hook is not the right place for it (the welcome is
  not an auth email and Supabase will not ask for one), but the hook proves the
  `signup` event is observable from our own server. The welcome belongs on the
  first successful `verifyOtp`, at
  `apps/web/src/lib/auth/actions.ts:433`, immediately after the session is
  established, wrapped in `bestEffortEmail`.
- **Local configuration**, if the local stack should behave the same:
  `supabase/config.toml` has no `[auth.hook.send_email]` block today. Supabase's
  hook environment variables are `GOTRUE_HOOK_SEND_EMAIL_ENABLED`,
  `GOTRUE_HOOK_SEND_EMAIL_URI` and `GOTRUE_HOOK_SEND_EMAIL_SECRETS`.

Route B risks, stated honestly, because `AUTH_EMAILS.md` raised them and they
are real:

- Our deployment being down becomes sign-up being down. Supabase retries on a
  non-2xx, which our route returns on any send failure (`route.ts:190`), so
  this is a delay rather than a loss, but it is still our uptime in the auth
  path.
- The secret is one more thing that can be forgotten in an environment. The
  route fails closed rather than open, which is the right direction.
- The five dashboard templates become dead weight. Keep them as the fallback if
  the hook is ever switched off, and say so in `AUTH_EMAILS.md`.

### My recommendation

Route B, because the code is already written, the six digit screen and the
inbox already agree on it, and it is the only route on which the reset email
can be ours. Route A as the documented fallback. Whichever is chosen,
`AUTH_EMAILS.md` needs rewriting: today it describes a decision the code does
not implement.

# PART 2. THE EMAIL DESIGN

## 2.1 What actually renders in an email client

This section is the honest version. Everything below is either cited, or
observable in this repository, or flagged as unverified.

### backdrop-filter: it does not work, so glass is not a filter

`backdrop-filter` is supported in Apple Mail, partially in Outlook, and **not
in Gmail or Yahoo Mail**
([caniemail](https://www.caniemail.com/features/css-backdrop-filter/)). Gmail is
the majority of this product's readers, so treating the glass card as a blurred
surface means the glass exists for a minority and the card is a flat nothing for
everyone else.

**So glass is faked with tone and edge, never with blur.** The recipe is in
2.2. This is already what the shipped shell does and the reasoning is written
down at `AUTH_EMAILS.md` section 3: "No mail client renders a backdrop blur, so
the card is `--nf-ink-850` with a one pixel rim in a lighter blue and the
luminous cap rule above it. Depth by tone, not by filter."

### border-radius: everywhere except classic Outlook on Windows

Classic Outlook for Windows renders with the Microsoft Word engine and does not
support `border-radius`
([Mailjet](https://documentation.mailjet.com/hc/en-us/articles/38816577432475-Outlook-rendering-issues),
[Emailens](https://emailens.dev/blog/outlook-css-guide)). A rounded card becomes
a square card there. That is an acceptable degradation and needs no VML: a
square card on our navy with our rim still reads as the product. The new Outlook
for Windows uses Edge WebView2 and supports rounded corners, gradients and
background images properly
([MailViewr](https://www.mailviewr.com/blog/classic-vs-new-outlook-rendering)),
and Microsoft has signalled the end of the Word engine desktop client around
October 2026, though both engines will be in any real audience for a long time
after that.

**Consequence for the shape law:** the product's shape law says every
text-bearing control is a rounded rectangle on `--nf-radius-control`, which is
14px (`packages/design-tokens/src/tokens.css:1835` resolving to
`--nf-radius-md: 14px` at `:1784`), and there is no capsule variant
(`docs/DESIGN_DIRECTION.md`, section 3 rule 4). Our email button is already
14px (`render.ts:310-311`). In classic Outlook it draws as a rectangle, which
is a squarer version of the same shape, never a capsule. The law is safe in
every client.

### CSS gradients: supported broadly, dropped by the Word engine

Classic Outlook drops `background-image`, which is how a CSS gradient is
declared, and keeps `background-color`
([Emailens](https://emailens.dev/blog/outlook-css-guide)). Every gradient
therefore needs a solid fallback colour declared **first**, on the same element,
so the Word engine paints the solid. Our shell already does this at three
places: the button (`render.ts:310`), the cap rule (`render.ts:464`) and the
footer dash (`render.ts:495`). Keep it. The ordering is the whole trick and it
is easy to undo by accident.

### Dark mode: three different behaviours, and only one of them is a media query

This is where a dark-first email is most at risk, and it deserves more candour
than our own comments currently give it.

- **Apple Mail and iOS** honour `color-scheme` and
  `@media (prefers-color-scheme: dark)`. Declaring `color-scheme: dark` tells
  them not to invert a palette we chose
  ([Litmus](https://www.litmus.com/blog/the-ultimate-guide-to-dark-mode-for-email-marketers)).
- **Gmail** applies its own dark mode logic and **strips
  `@media (prefers-color-scheme: ...)`**, and the Gmail app on Android
  recalculates luminance of backgrounds and text and inverts regardless of
  declared styles
  ([Mailpeek](https://mailpeek.dev/blog/dark-mode-email-rendering),
  [Emailens](https://emailens.dev/blog/dark-mode-email-guide)). Our shell's
  `DARK_STYLE` block (`render.ts:408-419`) is written as if the media query is
  what holds Gmail off. It is not. It helps Apple Mail and a handful of others
  and Gmail ignores it.
- **Outlook.com and Outlook Windows** invert light backgrounds to dark and
  leave dark areas alone, and strip standard media queries in webmail,
  requiring the `[data-ogsc]` and `[data-ogsb]` attribute selectors instead
  ([Customer.io](https://customer.io/learn/message-composing/email-forced-dark-mode)).

**What this means for a dark-first email, honestly.** A dark email is *safer*
than a light one under forced dark mode, because the clients that invert are
mostly inverting light to dark and leave dark alone. The real failure mode is
the opposite one: a client that lightens a background it judges too close to
its text, leaving pale text on a pale ground. The defence is not the media
query. The defence is:

1. **Every colour inline on the element it paints**, beside the background it
   sits on. This is the layer no client strips. Our shell does this.
2. **The ground painted three times**: on `<body>`, on the outer table as a
   `bgcolor` attribute, and on the card cell. `bgcolor` is the one form the
   Word engine has honoured since 2007. Our shell does this
   (`render.ts:452`, `:457`, `:466`).
3. **Contrast that survives a shift.** Body text at `#C6CDF2` on `#000030`
   measures about 12.9:1 and small print at `#7C86C2` about 5.6:1
   (`theme.ts:73-75`). Both have enough headroom that a client nudging the
   background a couple of rungs lighter still leaves readable text.
4. **Keep the media query anyway**, because it is free and it helps Apple Mail.
   Add the `[data-ogsc]` twin for Outlook.com. Do not believe it saves Gmail.

### Web fonts: do not ship one

Web fonts never display in Outlook for Windows, and the system stack is the
clean answer for transactional mail
([Warmy](https://www.warmy.io/blog/email-best-practices/best-email-safe-fonts-deliverability/),
[MiN8T](https://min8t.com/articles/web-safe-fonts-for-email)). Our theme already
refuses one and says so in a comment: "System stack only. A web font in an email
is a request that will not load" (`theme.ts:108`). The stack is
`-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, Helvetica, Arial,
sans-serif` (`theme.ts:109-110`) and the mono stack is
`'SFMono-Regular', Consolas, 'Liberation Mono', Menlo, monospace`
(`theme.ts:111`).

`font-family` has to be repeated on headings, because several clients reset
heading fonts to a serif default and inheritance from body does not save it
(`render.ts:242-243`).

### SVG: effectively unusable, which is a problem for our glass icons

Linked SVG is supported in Apple Mail and partially in Gmail; embedded inline
`<svg>` is not supported in Gmail, Outlook or Yahoo Mail
([caniemail](https://www.caniemail.com/features/image-svg/),
[caniemail](https://www.caniemail.com/features/html-svg/)). Outlook for Windows
on the Word engine has no SVG support at all
([AllSVGIcons](https://allsvgicons.com/blog/email-svg-icons/)).

**So our glass icon pack does not go in an email as SVG.** Three answers, in
order of preference:

1. **Do not use content icons in email at all.** This is what the shipped shell
   does and it is right. The only images in a Vallo email are the two lockup
   pieces. An email is one message with one action, and an icon rail is screen
   furniture that an inbox does not need.
2. Where an icon genuinely earns its place later, **export the glass object as a
   PNG at 2x**, host it under `/brand/`, give it an explicit `width` and
   `height` so a blocked image reserves its own box, and give it an empty `alt`
   if it is decorative.
3. Never a `<picture>` element with an SVG source and a PNG fallback. It works
   in the modern clients and buys nothing over shipping the PNG to everyone.

### Images blocked by default: the message must read with images off

Many Outlook versions and a large share of other inboxes block images until the
reader asks for them
([Mailosaur](https://mailosaur.com/blog/fix-rendering)). Every word that matters
must be live text.

Our shell already holds this line and there is a test that enforces it:
`shell.test.ts:173`, "every rendered email reads completely with images
blocked". The rules the shell obeys (`render.ts:61-66`):

- Two images only, both the lockup.
- The mark is decorative: `alt=""`, so a screen reader and an images-off inbox
  do not say "Vallo" twice.
- The wordmark is the word: `alt="Vallo"`, and it carries inline
  `font-family`, `font-size`, `font-weight`, `letter-spacing` and
  `color:#5C7CFF` so the alt text itself is styled as the brand word
  (`render.ts:478`).
- Both have explicit `width` and `height` so a blocked image reserves its box
  rather than collapsing the line.
- **The six digit code is live text, never a picture.** This is the single
  most important images-off rule in the system. A code baked into an image is
  a code nobody can copy and nobody can hear.

### Table layout, width, and the Gmail clipping limit

- **Tables only.** No flex, no grid, no positioning. The Word engine supports
  none of it, and it ignores `margin` and `padding` on `div` and `img`
  ([Emailens](https://emailens.dev/blog/outlook-css-guide)). Every table that
  is layout carries `role="presentation"` so a screen reader does not announce
  it as data.
- **600px, fluid below.** 600 is what the Outlook desktop reading pane fits
  without a horizontal scrollbar at the default window size (`theme.ts:117-121`).
  Below 600 the table is fluid so it reads on a 360px Android screen, which is
  the screen most of this product's readers have. Note that classic Outlook
  ignores `max-width`, so the outer table carries `width="100%"` and the inner
  one carries `max-width:600px;width:100%`, which is what our shell does
  (`render.ts:457`, `:460`).
- **Gmail clips past roughly 102KB** and hides the rest behind "View entire
  message". Google does not document the number, so treat 102KB as a reliable
  working figure and not an official one
  ([Alice Li](https://alicelicode.medium.com/does-gmail-clip-at-102kb-or-100kb-what-its-actually-counting-728c8c7497d2),
  [Mailchimp](https://mailchimp.com/help/gmail-is-clipping-my-email/)). On
  mobile the practical ceiling is lower.
  Our own budget is far tighter and for a better reason:
  `shell.test.ts:523-535` fails any message over **40,000 bytes**, because a
  reader on a metered Nigerian connection pays for every kilobyte. Measured
  today, the five auth templates are 10.2KB to 11.4KB each. Keep the 40KB
  budget. It is one of the better decisions in this codebase.
- **Padding lives on cells, not on tables.** Outlook drops padding declared on
  a table element (`render.ts:262-264`).
- **`mso-line-height-rule: exactly`** on any spacer row, or Word adds its own
  leading (`render.ts:464`, `:482`).
- **`mso-padding-alt`** on the button cell, because Word ignores padding on an
  inline-block (`render.ts:310`).

### The hidden line beside the subject

Every message needs one deliberate sentence that the inbox shows after the
subject, hidden in the body. Without it the client pulls the first words of the
body copy, which for a code email is "Hello there. Type this into the tab you
have open", which tells the reader nothing.

Our shell requires it, as a non-optional field on `ComposeOptions`
(`render.ts:384-385`), renders it as a fully collapsed span with
`mso-hide:all`, and pads it with zero-width and word-joiner entities so the
client cannot pull body copy in after it (`render.ts:456`).

It is **not** repeated in the plain text part, because in text there is nothing
to show ahead of the message and repeating it prints the same sentence twice
(`render.ts:517-524`).

### The fake glass recipe

Glass in this product is a blurred surface with a lit leading edge. Email gets
neither blur nor shadow reliably. So glass is rebuilt from three things that
every client can draw, and it degrades in a straight line rather than falling
over:

1. **Tone separation.** The ground is `#010118` and the card is `#000030`, one
   rung apart. The panel inside the card is `#000040`, one rung again. Three
   flat fills, each lighter than the one behind it, reads as depth without a
   single filter.
2. **A one pixel rim in a lighter blue**, `#2743C4`, on the card. This is the
   lit leading edge, and it is the part that actually says glass. It is a
   border, so it survives everywhere except where borders are dropped, and
   nothing drops a border.
3. **A 4px gradient cap rule** above the card, brightest at its centre:
   `linear-gradient(90deg,#0010D0 0%,#0C39EF 28%,#5C7CFF 50%,#0C39EF 72%,#0010D0 100%)`
   over `background-color:#0C39EF`. This is the light source. In classic
   Outlook the gradient is dropped and a solid electric blue bar remains, which
   is a plainer version of the same idea and not a broken one.

What is explicitly forbidden: `backdrop-filter`, `filter: blur()`, `box-shadow`
as the load-bearing depth signal, an image of a blurred card, and any
transparency that depends on the client compositing correctly. If a client
draws all three of the above, the card reads as lit glass. If it draws only the
tones and the border, it reads as a clean dark card. Both are Vallo.

### The code block, for a six digit verification code

```
┌────────────────────────────────────────────┐   #000040, 1px #101A55, radius 16px
│                                            │   20px vertical padding
│            4 8 2 9 0 1                     │   26px mono, 700, 0.2em tracking
│                                            │   centred, white
└────────────────────────────────────────────┘
```

Five decisions and the reason for each:

1. **Live text, never an image.** Images are off by default in a large share of
   inboxes, and an image of a code is a code that cannot be copied, cannot be
   read aloud and cannot be selected.
2. **Monospaced at 26px with 0.2em tracking**, so the digits are countable at a
   glance and a 0 cannot be mistaken for an O.
3. **`text-indent: 0.2em` to match the tracking.** Letter-spacing pushes a
   trailing space after the last glyph, which shifts an apparently centred
   string right. Putting the same amount back on the left recentres it
   (`render.ts:317-320`). This is the kind of thing a reader notices without
   being able to say why.
4. **No button in a code email, at all.** A code email teaches people what a
   code email looks like, and every phishing message that follows copies it. If
   the real one has a big blue button, the reader has been trained to press one
   (`messages.ts:408-421`). This is the strongest copy decision in the
   codebase and it must not be softened.
5. **The code is in the subject line too.** Most people read it off the
   notification without opening anything, which is faster and strictly safer
   (`messages.ts:417-419`).

On selection: a table cell of live text is selectable in every client that lets
you select anything. There is no reliable "copy" button in email, and
attempting one with a `mailto:` or a link is worse than the plain digits.

### The button, bulletproof, on our radius, never a capsule

```html
<table role="presentation" cellpadding="0" cellspacing="0" border="0" style="margin:10px 0 6px;">
  <tr>
    <td align="center" style="border-radius:14px;background-color:#0C39EF;background-image:linear-gradient(135deg,#0C39EF 0%,#0621E8 55%,#0010D0 100%);mso-padding-alt:16px 34px;">
      <a href="HREF" target="_blank" style="display:inline-block;padding:16px 34px;font-family:-apple-system,BlinkMacSystemFont,'Segoe UI',Roboto,Helvetica,Arial,sans-serif;font-size:16px;line-height:20px;font-weight:600;letter-spacing:-0.01em;color:#FFFFFF;text-decoration:none;border-radius:14px;">LABEL</a>
    </td>
  </tr>
</table>
```

- `background-color` **before** `background-image`, so the Word engine keeps a
  solid electric blue button with white text rather than white text on nothing.
- Padding on the anchor, not on the cell, so the whole button is a tap target on
  a phone.
- `mso-padding-alt` repeats the geometry for Word.
- `border-radius: 14px`, which is `--nf-radius-control`
  (`packages/design-tokens/src/tokens.css:1835` → `:1784`). The drawn shape is
  14px radius on a 52px tall button, a ratio of 0.27, comfortably under the 0.35
  the design direction says to look at and the 0.5 that makes a capsule
  (`docs/DESIGN_DIRECTION.md` section 3 rule 4). It is a rounded rectangle in
  every client that draws a radius, and a rectangle in the one that does not.
  There is no client in which it becomes a capsule.
- `color:#FFFFFF` written literally rather than through the palette, because it
  is the text on the brand blue in every scheme, not a themed value.

### The dark and light strategy, stated plainly

**There is no light version, and that is the decision.** The product is dark by
default and the operating system does not override it, so the email is the same
object as the screen it sends people to. The strategy is four layers, in the
order a client strips them:

1. **Inline styles on every element**, colour beside the background it sits on.
   Nothing strips this. This layer alone renders the email correctly.
2. **`bgcolor` attributes** on `<body>` and the outer table. The Word engine
   has honoured this since 2007 and it is the belt to the inline braces.
3. **`<meta name="color-scheme" content="dark">` and
   `<meta name="supported-color-schemes" content="dark">` plus
   `:root { color-scheme: dark; supported-color-schemes: dark; }`**, so Apple
   Mail and iOS do not invert a palette they did not design.
4. **`@media (prefers-color-scheme: dark)` re-asserting the same values with
   `!important`**, plus an `[data-ogsc]` twin for Outlook.com. This layer helps
   Apple Mail and a few others. Gmail strips it. Do not lean on it.

The test of the whole strategy: delete the `<style>` block and the email must be
exactly the same email. Our shell passes that test today
(`render.ts:398-419` and the note at `render.ts:55-59`).

The one addition I recommend over what ships now is the Outlook.com twin, which
is four lines and costs nothing:

```html
<style>
  :root { color-scheme: dark; supported-color-schemes: dark; }
  @media (prefers-color-scheme: dark) {
    .rm-base  { background:#010118 !important; }
    .rm-card  { background:#000030 !important; border-color:#2743C4 !important; }
    .rm-panel { background:#000040 !important; border-color:#101A55 !important; }
    .rm-title { color:#FFFFFF !important; }
    .rm-body  { color:#C6CDF2 !important; }
    .rm-muted { color:#7C86C2 !important; }
    .rm-rule  { border-top-color:#101A55 !important; }
    .rm-brand { color:#5C7CFF !important; }
  }
  [data-ogsc] .rm-base  { background:#010118 !important; }
  [data-ogsc] .rm-card  { background:#000030 !important; border-color:#2743C4 !important; }
  [data-ogsc] .rm-panel { background:#000040 !important; border-color:#101A55 !important; }
  [data-ogsc] .rm-title { color:#FFFFFF !important; }
  [data-ogsc] .rm-body  { color:#C6CDF2 !important; }
  [data-ogsc] .rm-muted { color:#7C86C2 !important; }
</style>
```

### The plain text alternative

Every message carries one, built from the same block list in the same order, so
the two cannot drift (`render.ts:517-535`). A text part maintained separately is
wrong within a month, and a wrong one is worse than none: it is what a screen
reader reads, what a text-only client shows, and what a spam filter compares
against the HTML. A message with no text part scores worse with every major
filter, because a missing alternative is a bulk-mail signature
(`render.ts:38-42`).

The rendering rules (`render.ts:351-379`):

- A heading is underlined with dashes, not shouted in capitals, because a screen
  reader spells an all-caps word out letter by letter.
- Rows are `Label: value`, one per line, never column aligned, because alignment
  padding needs a monospaced font and a proportional one turns it into ragged
  nonsense.
- A button becomes `Label:` then the URL on its own line.
- A code is the bare value on its own line.
- Paragraphs wrap at 72 characters; URLs are left whole so they stay clickable.
- The hidden inbox line is not repeated.

### Unsubscribe, and where it is and is not required

None of the three emails in 2.3 carries an unsubscribe link, and that is
correct. All three are transactional: a person asked for a code, asked for a
reset, or just created an account. There is nothing to unsubscribe from.

What they carry instead is the honest one line that says why the message
arrived, which is what a real auth email does and what a phishing copy usually
omits:

> You are receiving this because a code was requested for this address on Vallo.

Where unsubscribe **is** required:

- Anything on the `marketing` channel (`recipients.ts:39`): a digest, a saved
  search alert, a recommendation, an offer. Those need a working one-click
  unsubscribe, a `List-Unsubscribe` header and a `List-Unsubscribe-Post`
  header, because the large mailbox providers now require one-click unsubscribe
  for bulk senders. Our Resend client does not send custom headers today
  (`client.ts:118-127` builds a fixed body), so that is a build task on the
  client, not just on a template.
- The notification-style emails on `bookings`, `messages` and `wallet` sit in
  between. They are transactional, but the settings card promises they can be
  switched off, and `emailMuted` (`recipients.ts:51`) already honours that. Put
  a plain "Change what Vallo emails you" link to `/settings/notifications` in
  the footer of those, rather than an unsubscribe.

Copy rules held in all three: British spelling, zero em dash characters, no
emoji, no escrow promise, no claim that a listing has been checked, none of the
forbidden words, and every message says plainly what happens if the reader does
nothing.

The templates use one placeholder convention, `{{ }}`, so they can be filled by
either the Supabase dashboard (`{{ .Token }}`, `{{ .SiteURL }}`) or by our own
renderer. Where a value differs between the two, I have noted it.

# PART 3. NOTIFICATIONS END TO END

## 3.1 The one door

Every in-app notification goes through one writer.

```sql
private.notify(target_user uuid, n_kind notification_kind,
               n_title text, n_body text, n_href text)
```

- Created at `supabase/migrations/20260729112606_notifications.sql:41`.
- Rewritten to honour preferences at
  `supabase/migrations/20260804134543_notification_preferences_are_honoured.sql:27`.
- `security definer`, `search_path = public`, and `execute` revoked from
  `public`, `anon` and `authenticated`
  (`20260729112606_notifications.sql:58-59`).

The table it writes (`20260729112606_notifications.sql:22-30`):

```sql
public.notifications (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  kind public.notification_kind not null,
  title text not null,
  body text,
  href text,
  read_at timestamptz,
  created_at timestamptz not null default now()
)
```

Kinds: `booking`, `message`, `wallet`, `listing`, `agent`, `support`, `system`
(`20260729112606_notifications.sql:11-19`), plus `social` added at
`supabase/migrations/20260804105241_notification_kind_social.sql:9`.

Row level security (`20260729112606_notifications.sql:184-200`): owners select,
update and delete their own. **No client insert at all.** Rows come only from
triggers and the service role. The update grant is column scoped to `read_at` so
a client cannot rewrite history.

Preference enforcement, and it is narrower than people assume
(`20260804134543_notification_preferences_are_honoured.sql:47-73`):

- Only `booking` and `message` kinds can be silenced in app.
- **Wallet is always delivered in app whatever the switch says**, because a
  reversed withdrawal is money at risk. The switch still silences wallet email.
  The migration argues this out loud at its lines 17-22.
- Absent or malformed settings mean deliver. Only an explicit `false` silences.
- The `jsonb_typeof` guard is load-bearing: a bare `::boolean` cast on a value
  an older client wrote raises 22P02 inside the trigger and takes the whole
  booking write down with it (`:54-58`).

## 3.4 Leg two: email. Partly built, and the split is structural.

Of the roughly thirty-six in-app events, **nine have an email**: booking
requested for both sides, booking confirmed, arrival details, booking
cancelled, booking refunded, wallet funded, withdrawal failed, support ticket
filed. Every one of those nine is sent from a Next.js server action or an API
route, never from the database.

Everything the database writes on its own has no email. That is the structural
point from 1.4 restated from the other side: **the email layer and the
notification layer do not meet.** They are two independent fan-outs that happen
to cover overlapping events, and where an event is only covered by a trigger, it
is in-app only.

Three ways to close it, with an honest cost for each:

1. **Add a send beside each server action that already writes.** Cheapest,
   works today, no new infrastructure. Does nothing for events that only a
   trigger produces (inspections, moderation, social, payout accounts, reports).
2. **A database webhook on `public.notifications` insert**, posting to a new
   Next.js route that maps `kind` plus `title` to a catalogue message. One
   integration covers every present and future trigger. The cost is that the
   mapping is by string, which is fragile, and that it needs a `kind`-to-channel
   policy so a reader is not emailed about every like.
3. **An outbox table and a scheduled worker.** A trigger writes an
   `email_outbox` row alongside the notification; a cron job drains it through
   the catalogue. Most robust, most retryable, most code. This is also the shape
   that digesting needs, so it is the shape that scales.

My recommendation: 1 now for the ten unsent messages, 3 as the target, and skip
2. Option 2 looks cheap and puts business logic in string matching.

### 3.7.1 Close the email column

```sql
-- NOT APPLIED. Proposed schema for a build session.
create table public.email_outbox (
  id           uuid primary key default gen_random_uuid(),
  user_id      uuid not null references auth.users (id) on delete cascade,
  -- The catalogue key, not a rendered message. Rendering happens in Node,
  -- where the shell lives, so a template change reaches queued mail.
  template     text not null,
  payload      jsonb not null default '{}'::jsonb,
  -- Which settings switch governs this. Null means it cannot be muted,
  -- which is correct for a security notice.
  channel      text check (channel in ('bookings','messages','wallet','marketing')),
  status       text not null default 'pending'
                 check (status in ('pending','sending','sent','failed','skipped')),
  attempts     smallint not null default 0,
  last_error   text,
  send_after   timestamptz not null default now(),
  created_at   timestamptz not null default now(),
  sent_at      timestamptz
);

create index email_outbox_due_idx
  on public.email_outbox (send_after)
  where status = 'pending';

alter table public.email_outbox enable row level security;
-- No policy at all: only the service role reads or writes this table.
```

A worker route drains it: select due rows, mark `sending`, render through the
catalogue, `sendMessage`, mark `sent` or `failed` with a backoff on
`send_after`. Cap attempts at three. The worker is the one place a retry is
allowed, because everywhere else `bestEffortEmail` swallows by design.

### 3.7.2 The push token table

```sql
-- NOT APPLIED. Proposed schema for a build session.
create type public.push_platform as enum ('web', 'ios', 'android');

create table public.push_tokens (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references auth.users (id) on delete cascade,
  platform      public.push_platform not null,

  -- For ios and android this is the FCM or APNs registration token.
  -- For web it is the PushSubscription endpoint URL.
  token         text not null,

  -- Web Push only. Null on native. Both are base64url from the browser's
  -- own subscription and are useless without the private VAPID key.
  p256dh        text,
  auth          text,

  -- So a person can recognise and revoke a device they no longer have.
  device_label  text,
  app_version   text,

  created_at    timestamptz not null default now(),
  last_seen_at  timestamptz not null default now(),
  -- Set when the provider tells us the token is dead. Never deleted
  -- immediately, so a re-registration from the same device is an update
  -- rather than a duplicate.
  revoked_at    timestamptz,

  -- One row per token, ever. A token that moves to another account is an
  -- update of user_id, not a second row, or the old owner keeps receiving
  -- the new owner's notifications. This is the single most common bug in
  -- a push implementation and the constraint is the fix.
  unique (token)
);

create index push_tokens_user_idx
  on public.push_tokens (user_id)
  where revoked_at is null;

alter table public.push_tokens enable row level security;

-- A person may register their own device, see their own devices and revoke
-- one. They may never read anybody else's, because a token is a capability
-- to send to that device.
create policy push_tokens_select_own on public.push_tokens
  for select using ((select auth.uid()) = user_id);

create policy push_tokens_insert_own on public.push_tokens
  for insert with check ((select auth.uid()) = user_id);

create policy push_tokens_update_own on public.push_tokens
  for update using ((select auth.uid()) = user_id)
             with check ((select auth.uid()) = user_id);

create policy push_tokens_delete_own on public.push_tokens
  for delete using ((select auth.uid()) = user_id);
```

Note the `(select auth.uid())` form rather than bare `auth.uid()`. This
repository already moved to it for the initplan optimisation
(`supabase/migrations/20260729174306_rls_initplan_and_fk_index.sql`), so a new
table should be written that way from the start.

The sending side is a worker like the email one, reading
`public.notifications` inserts or its own `push_outbox`, looking up live
tokens, and posting to FCM for Android and web and to APNs for iOS. Web Push
needs a VAPID key pair; the private half is a server-only environment variable
and the public half is compiled into the client.

New environment variables, to add to `apps/web/.env.example`:

```
# Web Push. Generate once with `npx web-push generate-vapid-keys`.
NEXT_PUBLIC_VAPID_PUBLIC_KEY=
VAPID_PRIVATE_KEY=            # SERVER ONLY
VAPID_SUBJECT=mailto:hello@vallospaces.com

# Firebase Cloud Messaging, for Android and for the web transport.
FCM_PROJECT_ID=
FCM_SERVICE_ACCOUNT_JSON=     # SERVER ONLY, the whole JSON

# Apple Push Notification service, for iOS.
APNS_KEY_ID=
APNS_TEAM_ID=
APNS_PRIVATE_KEY=             # SERVER ONLY, the .p8 contents
APNS_BUNDLE_ID=
```

Native files that do not exist and must be added, with the note that both are
secrets in the sense that they should not be in a public repository:
`apps/web/android/app/google-services.json`, and
`apps/web/ios/App/App/GoogleService-Info.plist` if FCM is used on iOS as well.
iOS also needs the `aps-environment` entitlement and
`UIBackgroundModes` containing `remote-notification`, and the Capacitor plugin

### 3.7.3 The permission request, and the rules that are not negotiable

The Android manifest comment already states the principle: do not spend the one
prompt a person reliably grants on a channel that cannot deliver anything. The
corollary is that the prompt must be earned, not asked for at launch.

**The universal rule.** Never call the system prompt from a cold start. Show a
Vallo-designed explanation first, in the glass register, that says exactly what
will be sent and offers Not now. Only a Yes on that screen may call the system
API. A system prompt declined is, on iOS, effectively permanent: the only way
back is the Settings app, and most people never go.

**When to ask.** At the first moment the value is obvious and the person is
already succeeding at something:

- A host, immediately after their first listing is published. The offer is
  "Know the moment somebody asks about it."
- A guest, immediately after their first booking request is sent. The offer is
  "Know the moment the host answers."
- A person, on their second reply in a conversation. The offer is "Know when
  they write back."

Never on the home screen, never on sign-up, never on a payment screen.

**iOS.** The permission is requested with `UNUserNotificationCenter`. Ask for
alert, badge and sound in one request. Consider the provisional authorisation
option, which delivers quietly to Notification Centre without a prompt and lets
the person promote it to full delivery from the notification itself; it is the
gentlest possible first ask and it costs nothing if ignored. Whatever is chosen,
register with APNs only after authorisation, and store the token through the
table above.

**Android 13 and above.** `POST_NOTIFICATIONS` is a runtime permission. It must
be added to the manifest, which today deliberately omits it
(`apps/web/android/app/src/main/AndroidManifest.xml:294-298`), and that comment
must be rewritten when it is, because leaving a comment that says the opposite
of the manifest is how the next reader is misled. Request it with the standard
runtime request flow after the Vallo explanation screen, and handle the
permanent denial state by routing to the app's notification settings rather than
re-prompting. Below Android 13 the permission is granted at install and no
prompt exists, so the explanation screen should not be shown there at all.

**Web push.** `Notification.requestPermission()` must be called from a user
gesture, in the same tick as the click. iOS Safari grants web push only to a
site installed to the home screen, so on iOS the web path must offer the install
step first or offer nothing. A denied permission cannot be re-prompted from the
page and the person has to change it in browser settings, so the Vallo screen
must make the stakes clear before the gesture.

**Re-asking.** Once. If somebody declines the Vallo screen, wait at least thirty
days and one further qualifying moment before offering again, and never offer a
third time.

### 3.7.4 The preference surface, including quiet hours

Today `/settings/notifications` writes four booleans into
`profiles.settings.notifications`: `bookings`, `messages`, `wallet`,
`marketing` (`recipients.ts:39`, read at `recipients.ts:51-70` for email and at
`20260804134543_...sql:47-73` for in-app). One switch governs two channels,
which was fine when there were two channels.

With push there are three, and one boolean per topic can no longer express what
people want. The shape that does is a grid:

```
                        In app    Email    Push
Bookings and stays        [x]      [x]      [x]
Messages                  [x]      [ ]      [x]
Money                     [x]*     [x]      [x]
Your listings             [x]      [x]      [x]
Around: people            [x]      [ ]      [ ]
Around: moderation        [x]      [x]      [ ]
Ideas and offers          [ ]      [ ]      [ ]

  * Money in app cannot be switched off. The row says so in place.
```

Storage, extending the existing document rather than replacing it so nothing
already written breaks:

```json
{
  "notifications": {
    "bookings": true,
    "messages": true,
    "wallet": true,
    "marketing": false,

    "channels": {
      "bookings":   { "app": true, "email": true,  "push": true },
      "messages":   { "app": true, "email": false, "push": true },
      "wallet":     { "app": true, "email": true,  "push": true },
      "listings":   { "app": true, "email": true,  "push": true },
      "social":     { "app": true, "email": false, "push": false },
      "moderation": { "app": true, "email": true,  "push": false },
      "marketing":  { "app": false,"email": false, "push": false }
    },

    "quiet_hours": {
      "enabled": true,
      "from": "22:00",
      "to": "07:00",
      "timezone": "Africa/Lagos"
    }
  }
}
```

Reading rules a build session must implement exactly:

1. **The old booleans stay authoritative where the new object is absent.** A
   missing `channels` key means fall back to the four booleans, and a missing
   boolean means deliver. The existing `jsonb_typeof` guard pattern applies to
   every read (`20260804134543_...sql:54-58`).
2. **Quiet hours apply to push only.** They never delay an email, because an
   email already waits in an inbox, and they never suppress an in-app row,
   because that row is the record. A push that falls inside quiet hours is
   **held until the window ends, then collapsed**: one notification saying how
   many things happened, not eleven at seven in the morning.
3. **Quiet hours never apply to a security or money-at-risk event.** A reversed
   transaction, a failed withdrawal, a payout account added, a password changed,
   a sign-in from a new device: these go straight through at any hour. This is
   the same argument the database already makes for keeping wallet notifications
   unmutable in app (`20260804134543_...sql:17-22`), extended to push.
4. **The timezone is stored, not inferred.** Default to `Africa/Lagos`, offer to
   change it, and evaluate the window in that zone rather than in UTC or in the
   device's current zone, so a person travelling does not get woken at what is
   night where they actually are.
5. **A device list belongs on this screen.** Each row from `push_tokens` with
   its `device_label` and `last_seen_at`, and a Revoke control that sets
   `revoked_at`. Without it, push is a permission a person cannot take back
   except by uninstalling.

Digesting, which the matrix implies and nothing in the product has yet:

- Likes, reposts, follows and mentions must never be one push each. Collapse to
  one per person per hour, or one per thread.
- A daily digest email is a `marketing` channel message and needs the
  unsubscribe work in 2.2.
