# End-to-end audit, 29 September 2026

What this covers: every main flow, run in Chromium against the live dev server (`next dev -p 3210`, Supabase project `uccixoonmbhrnyczyigt`, `VALLO_PREVIEW_HARNESS=1`), at 390px and 1440px, in light and dark. The existing browser specs in `apps/web/tests/` were run too, through `run.mjs --tier full`.

Screenshots are in `/tmp/claude-0/-home-user-read-it-well/1f6b951d-e7a6-5422-90c7-ea17c43968d4/scratchpad/e2e/`. The rest of this document calls that folder `e2e/`. The scripts that produced the evidence are in the same folder: `walk.mjs` (route walker), `flows.mjs` (interactive flows), and the raw results in `public.json`, `preview.json`, `flows.json`, `specs-full.log` and `public-spec-fails.txt`.

## Limits of this run (read first)

- **No signed-in QA account was available.** `QA_MEMBER_EMAIL` and `QA_MEMBER_PASSWORD` are not set, and I did not create, reset or invent any credentials. Every signed-in surface was therefore tested in two ways:
  - The signed-out gate, checked on the real routes.
  - The same components in the preview harness (`/preview/...`), which renders them with fixture data.
  The real `/home`, `/search`, `/listing/[id]`, `/stay/[id]`, `/checkout/[id]`, `/profile`, `/settings`, `/notifications`, `/support`, `/agent/*`, `/host/*` and `/admin/*` pages have **not** been rendered with real data by this audit.
- **No payment was made.** Checkout was checked up to the point where the pay controls are present and enabled. They were never clicked, and no request went to `paystack.co`. The only "paystack" traffic was the local bundle chunk for `@paystack/inline-js`.
- **No sign-up was submitted.** The two-step form was driven through step 1, step 2 and back. Create account was never pressed.
- **Disk incident during the run.** The root filesystem was at 100%: 14 MB free, because `apps/web/.next/dev/cache/turbopack` had grown to 24 GB. Chromium was crashing ("Page crashed", `writev: No space left on device`), and the first spec run failed on that alone.
  - I deleted the Turbopack dev cache. It regenerates.
  - Because the running dev server still held the deleted files through mmap, I also restarted `next dev -p 3210`, with the same command and the same log file.
  - The disk went from 100% to 36% used. This cache will grow back. See issue O-1.
